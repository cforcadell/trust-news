Necesito implementar una evolución del flujo de generación de aserciones, búsqueda de evidencias y validación contextual.

Restricción principal:

NO modificar el smart contract.
NO cambiar eventos blockchain.
NO cambiar estructuras on-chain.
NO añadir nuevos parámetros al contrato.
NO modificar el formato de los eventos ValidationRequested / ValidationSubmitted.

Sí se puede cambiar el schema del documento JSON que se sube a IPFS.
Sí se puede cambiar el schema de mensajes Kafka.
Sí se puede cambiar el schema persistido en MongoDB.
No es necesario mantener compatibilidad con el schema actual.
Puedo borrar los datos actuales de Mongo/IPFS/local si hace falta.

Objetivo:

El sistema debe tener un único schema nuevo para las aserciones enriquecidas, usado tanto en modo BLOCKCHAIN como en modo LIGHT.

La información contextual de cada aserción debe incluir:

- categoría
- subcategoría
- localización
- jurisdicción
- entidades mencionadas
- marco temporal
- idioma
- tipos de fuente preferente
- keywords de búsqueda
- queries sugeridas
- confianza del contexto detectado

Esta información NO debe ir a blockchain.
Debe viajar en:

- documento JSON subido a IPFS en modo BLOCKCHAIN
- mensaje Kafka inline en modo LIGHT
- MongoDB si aplica para trazabilidad y consulta

El smart contract seguirá referenciando el CID del documento IPFS exactamente igual que ahora.

====================================================================
1. Principio arquitectónico
====================================================================

El contrato sigue siendo un ancla de trazabilidad e integridad.

El contenido funcional de validación vive fuera de la blockchain:

Modo BLOCKCHAIN:

generate-asertions genera documento enriquecido
  -> news-handler/news-chain sube documento enriquecido a IPFS
  -> smart contract guarda/referencia el CID como hasta ahora
  -> evento ValidationRequested se emite como hasta ahora
  -> news-chain o el validador recupera el documento desde IPFS
  -> se localiza la aserción correspondiente
  -> se construye AssertionValidationPayload v2
  -> validate-asertions recibe la misma estructura funcional que en LIGHT

Modo LIGHT:

generate-asertions genera documento enriquecido
  -> news-handler NO sube a IPFS
  -> news-handler NO llama a blockchain
  -> news-handler construye AssertionValidationPayload v2 inline
  -> lo envía por Kafka
  -> validate-asertions recibe la misma estructura funcional que en BLOCKCHAIN

Resultado deseado:

validate-asertions debe consumir el mismo payload lógico en ambos modos.

====================================================================

No mantener compatibilidad con el schema anterior.

====================================================================
5. Cambios en news-handler
====================================================================

news-handler debe trabajar con assertions-document-v2 como contrato interno.

En modo LIGHT:

- Recibe assertions-document-v2 desde generate-asertions.
- Persiste en Mongo si aplica.
- No sube a IPFS.
- No llama a news-chain.
- Por cada aserción, construye assertion-validation-payload-v2 con source_document.storage = inline.
- Publica en Kafka el payload v2 para los validadores.

En modo BLOCKCHAIN:

- Recibe assertions-document-v2 desde generate-asertions.
- Persiste en Mongo si aplica.
- Sube el documento completo enriquecido a IPFS.
- Llama al flujo blockchain existente pasando el CID como hasta ahora.
- No cambia smart contract.
- No cambia eventos.
- No cambia ABI.
- Asegura que el documento IPFS contiene schema_version assertions-document-v2.
- No construir payload incompleto: los validadores deben poder recuperar toda la info desde IPFS.

6. Cambios en news-chain
====================================================================

No modificar smart contract.

No modificar ABI.

No modificar eventos.

No modificar parámetros on-chain.

Solo adaptar lógica off-chain.

Cuando news-chain procese eventos ValidationRequested:

- Obtener el CID del documento IPFS como hasta ahora.
- Descargar el documento JSON desde IPFS.
- Validar que schema_version = assertions-document-v2.
- Localizar la aserción usando assertion_index del evento.
- Construir assertion-validation-payload-v2.
- source_document.storage = ipfs.
- source_document.cid = CID del documento.
- Enviar al topic Kafka o al mecanismo existente para validate-asertions el payload v2 completo.

Si el documento IPFS no es assertions-document-v2:

- Fallar con log claro.
- No intentar fallback legacy.

7. Cambios en validate-asertions
====================================================================

validate-asertions debe aceptar exclusivamente assertion-validation-payload-v2.

Eliminar o dejar de usar parsing legacy si existe.

Validar con Pydantic:

- schema_version
- mode
- assertion
- source_document

Para cada tipo de validador:

LLM_MEMORY_VALIDATION:
- Usar assertion.text.
- Usar assertion.context como apoyo semántico.
- No buscar en internet.

LLM_SEARCH_VALIDATION:
- Usar assertion.text, context y search_hints.
- Si el proveedor permite online search, activar online search.
- Si no puede restringir dominios, añadir dominios preferentes o instrucciones al prompt solo como orientación.

RAG_EVIDENCE_VALIDATION:
- Llamar a evidence-search con assertion completa.
- Usar las evidencias devueltas para validar.
- No buscar directamente en internet desde validate-asertions.
- El prompt debe indicar que solo puede razonar con las evidencias recibidas.

DETERMINISTIC_VALIDATION:
- Puede usar context para decidir fuente estructurada o dataset si existe.

HUMAN:
- Debe poder presentar assertion, context, search_hints y evidences si existen.

- no tocar news
- no tocar validations
- no tocar events
- no tocar clients_quotas

python scripts/k8s/apis/init-evidence-search-domains.py --refresh

Debe ser obligatorio para operaciones destructivas o de reemplazo real.

python scripts/k8s/apis/init-evidence-search-domains.py --refresh --confirm
