# OAuth para integraciones API — identidad propia por integración

**Estado:** diseño con implementación local en el árbol de trabajo; retirada efectiva de `TrustNewsApi`, aceptación y despliegue pendientes. `S03_INTEGRATIONS_ENABLED=false` por defecto. **Hito:** v0.0.13d, antes de habilitar acceso autónomo. No acredita el GO de v0.0.13b ni el de v0.0.13c. [Alta y mantenimiento](../../security/s03-api-integrations.md).

## Alcance y punto de partida

Cada integración que invoque la API tendrá un cliente confidencial **nuevo** y propio en Keycloak, incluso si varias integraciones pertenecen a la misma organización. El cliente usará `client_credentials` y su cuenta de servicio; una credencial no se compartirá entre integraciones ni organizaciones. `TrustNewsApi` quedará en desuso para integraciones: no se migrarán sus clientes, credenciales ni tokens al nuevo modelo, ni se aceptará como presentador de integraciones después del corte. Un consumidor que quiera seguir usando la API deberá darse de alta como integración nueva.

El cliente `TrustNewsWeb` y todo el inicio de sesión OpenID Connect de usuarios GUI conservan su contrato actual: configuración del cliente, redirecciones, scopes, tokens, refresh, logout, validación, membresías y cuotas humanas. El cambio del motor S03 debe conservar las rutas y datos usados por la GUI. Tampoco se reutilizarán como identidades externas los clientes de servicio internos `assermetry-*`.

Hoy Gateway acepta los presentadores configurados en `KEYCLOAK_ALLOWED_CLIENT_IDS` (por defecto `TrustNewsWeb,TrustNewsApi`) y `get_computed_client_id` deriva una clave histórica de cuota/propietario a partir del token. `reconcile_s03_keycloak.py` aprovisiona clientes **internos** y audiencias a partir de `s03-keycloak-clients.json`; `provision_s03_gui_user.py` aprovisiona **usuarios GUI** y sus cuotas. Admin mantiene `clients_quotas` con `client_id`; sus rutas `/clients` no constituyen un alta de clientes Keycloak. El verificador y la política S03 de `api/common/security/engine.py` ya proporcionan la base común para firma, emisor, audiencia, `azp`, cuenta de servicio y autorización. El flujo actual de rutas con `user_required` y `scope=own` presupone un humano: admitir integraciones requiere ampliar ese contrato, no añadir excepciones por cliente a cada endpoint.

## Contrato de identidad y autorización

1. Keycloak emite el access token de la integración para la audiencia de Gateway mediante `client_credentials`. El cliente es confidencial, tiene cuenta de servicio, `standardFlowEnabled=false` y `directAccessGrantsEnabled=false`; no recibe roles globales de administración. Cada cliente solo obtiene las audiencias y acciones aprobadas. El secreto se entrega por canal privado, nunca por Git, ConfigMap, URL o log.
2. Gateway y cada destinatario que reciba la identidad de la integración verifican firma, algoritmo, `iss`, `aud`, `exp`, `iat`, `nbf` si existe, `azp` y `sub`; exigen que el token corresponda a una cuenta de servicio. El par `issuer + azp + sub` debe resolver exactamente una asociación **activa**, creada en el alta nueva. `azp` identifica el cliente presentador; `sub` por sí solo no identifica a la organización. `TrustNewsApi` no constituye una asociación válida. Un token humano de `TrustNewsWeb` sigue el flujo humano existente.
3. La asociación persistida contiene `integration_id` estable, `org_id`, `issuer`, `azp`, `sub`, identificador Keycloak del cliente, estado, vigencia, acciones permitidas y referencia de cuota. Índices únicos para `issuer + azp`, `issuer + azp + sub` e `integration_id`; una discrepancia, duplicado, organización suspendida o asociación ausente falla cerrada. La asociación a organización no se modifica para trasladar una integración: se da de baja y se crea otra identidad.
4. El motor S03 representa explícitamente al actor `human` o `integration` y aplica la misma matriz declarativa por ruta, acción, audiencia, actor y alcance. Las rutas que exigen operador humano continúan exigiéndolo; una cuenta de servicio externa no hereda `trust-admin`, `trust-read-all` ni permisos de un usuario GUI. Gateway obtiene su propio token interno para llamar a News Handler/Admin y propaga el access token externo solo por saltos declarados. El destinatario verifica ambos tokens y resuelve el propietario desde datos persistidos. Ningún `client_id`, `org_id`, cabecera de actor o parámetro enviado por el llamante decide identidad o acceso.
5. Las operaciones de integraciones nuevas guardan `org_id` e `integration_id` para atribución. Su clave de cuota es estable y distinta del `client_id` de Keycloak; no se calcula a partir de `sub` ni del nombre del cliente. Las rutas de integraciones no usan `client_id` histórico como propietario ni como clave de cuota, y no trasladan automáticamente órdenes o consumos de `TrustNewsApi` a una integración nueva. Las rutas humanas y sus datos históricos permanecen bajo el contrato GUI existente.

## Cuota y ciclo de vida

La autorización de una llamada requiere integración y organización activas, acción permitida y cuota vigente. Cada alta nueva recibe límites aprobados expresamente; no hereda saldos ni consumos asociados a `TrustNewsApi`. La implementación local reserva, consume o libera gasto de generación con una actualización atómica por organización: comprueba el límite de organización y el de integración en el mismo documento, con `Idempotency-Key` y hash del cuerpo. Kafka omite el cobro duplicado de estas órdenes. Los límites `BLOCKCHAIN` quedan configurables pero su ejecución para integraciones se rechaza hasta implementar y aceptar su cobro. La cuota humana de `clients_quotas` y el flujo `TrustNewsWeb` conservan su comportamiento. La reserva/cobro y la recuperación de fallos aún requieren aceptación con MongoDB/Kafka reales.

El estado operativo de cada integración es `pending`, `active`, `suspended` o `retired`, con vigencia explícita y auditoría de alta, cambio y baja. El alta deja el cliente Keycloak deshabilitado hasta comprobar asociación S03, política y cuota; solo entonces lo habilita. La rotación sustituye el secreto con entrega privada y ventana controlada, comprueba el nuevo acceso y retira el anterior; si cambia `sub` o el identificador del cliente, exige nueva asociación revisada. Suspensión/baja bloquea nuevas peticiones en Gateway y destinatarios, deshabilita el cliente Keycloak, invalida cachés pertinentes y verifica el rechazo tras la vigencia máxima de tokens ya emitidos. El trabajo ya iniciado y los mensajes Kafka requieren política de cancelación/compensación explícita en S06/S07b; deshabilitar Keycloak por sí solo no revoca un JWT todavía válido.

| Gateway, News Handler y Admin | Resolver la asociación nueva en servidor, propagar/verificar identidad externa por los saltos autorizados y aplicar organización, propietario y cuota. Retirar `TrustNewsApi` de la admisión de integraciones y dejar intacto el flujo humano `TrustNewsWeb`. |
| `scripts/security/reconcile_s03_keycloak.py` y su configuración | Mantener su inventario de servicios internos y extraer/adaptar la operación común de conciliación de clientes confidenciales y audiencias para el alta de integraciones. | Motor de alta/mantenimiento de integraciones | Crear y conciliar **solo clientes nuevos** junto con `cuenta de servicio + asociación S03 + política + cuota` por `integration_id`; ofrecer vista previa sin escrituras, contexto explícito, hash del plan revisado y aplicación idempotente. Rechazar la adopción de `TrustNewsApi` o de credenciales compartidas. Incluir rotación, suspensión, reactivación y baja con verificaciones y recuperación ante pasos parciales. Reutilizar las comprobaciones de contexto, plan y archivos privados del alta GUI donde proceda, sin alterar `provision_s03_gui_user.py`. El conciliador web deja de asignar audiencia a `TrustNewsApi` y conserva el comportamiento de `TrustNewsWeb`. |
| Rutas Admin `/clients` y almacenamiento de cuotas | Definir la relación estable entre integración, organización y cuota; evitar que crear o borrar una fila de cuota se interprete como crear o revocar una identidad OAuth. Conservar el historial de consumo y la atribución al dar de baja. |

La vista previa muestra identidades técnicas, estado, acciones, audiencias, límites y diferencias sin secretos ni tokens. Aplicar exige destino/contexto explícito y el hash exacto del plan; relee Keycloak y MongoDB antes de escribir, bloquea conflictos y registra pasos compensables. Las credenciales permanecen en almacenamiento privado separado de los archivos versionados y de los scripts sincronizados por CI. El operador decide límites y vigencia; el motor no copia por defecto la cuota de otra integración.

## Secuencia y aceptación pendiente

1. Inventariar los usos de `TrustNewsApi` para preparar su retirada y decidir la conservación o archivo de órdenes y consumos históricos. Este inventario no transfiere identidad, credenciales, propietario ni cuota a los clientes nuevos. Si un consumidor anterior continúa, tramitar un alta nueva con límites y permisos aprobados.
2. Implementar el contrato de actor y políticas comunes y el motor de alta de integraciones. Probar clientes confidenciales nuevos, asociaciones S03 y cuotas separadas. En el corte, retirar `TrustNewsApi` de los presentadores admitidos para integraciones y deshabilitar su uso compartido en Keycloak; los tokens antiguos de integraciones dejan de autorizar peticiones. Mantener `TrustNewsWeb` y el flujo humano efectivos durante todo el corte.
3. Aceptar en kind con al menos dos integraciones de la misma organización y una de otra: identidad y cuota independientes; acceso propio permitido; lectura/escritura cruzada, `azp`/`aud` incorrectos, asociación ausente/suspendida, cuota agotada y rol humano requerido rechazados. Comprobar que un token de `TrustNewsApi` ya no da acceso como integración ni se le asignan cuotas nuevas. Probar reintentos concurrentes, rotación, baja y token emitido antes de la baja; comprobar que login, refresh, logout, rutas y cuotas GUI con `TrustNewsWeb` conservan su comportamiento.
4. Repetir aceptación en Hetzner/K3s sobre un SHA, imágenes, configuración y políticas efectivos, con datos desechables y evidencia de costes, logs depurados, rollback y revocación. Hasta entonces el acceso API autónomo continúa **NO-GO**.
